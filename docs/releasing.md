# npm releases

Skill Shelf is an npm CLI package, not a skills.sh skill. Releases use [Release Please](https://github.com/googleapis/release-please-action) and npm trusted publishing. Maintainers decide when to release by reviewing and merging the generated release PR; it is not auto-merged.

## Release policy

- Merge Conventional Commits into `main` (use a Conventional Commit squash title for PRs). Release Please maintains a PR updating `package.json`, `package-lock.json`, the release manifest, and `CHANGELOG.md`.
- `fix:` bumps patch. `feat:` bumps minor. While below 1.0, breaking changes (`!` or `BREAKING CHANGE:`) bump minor, not major. From 1.0, breaking changes bump major. Other commit types alone do not normally create a release.
- Only stable `vMAJOR.MINOR.PATCH` versions publish, to npm's `latest` dist-tag. A 0.x version is not an npm prerelease. Prereleases and alternate release branches are not configured. For an intentional 1.0 release, use Release Please's [Release-As override](https://github.com/googleapis/release-please#how-do-i-change-the-version-number) and review the generated PR.
- The initial manifest records the existing npm version `0.1.0`. `bootstrap-sha` identifies main's npm-distribution commit, excluding that history from the first generated changelog. The next `feat:` proposes `0.2.0`; a lone `fix:` proposes `0.1.1`.

`CHANGELOG.md` is generated by Release Please and excluded from Prettier; review its contents in the release PR.

## One-time setup

An owner must complete these steps; the workflow does not configure account or repository settings.

1. In GitHub repository **Settings → Actions → General → Workflow permissions**, enable **Allow GitHub Actions to create and approve pull requests**. Keep the default token read-only; individual jobs request their required permissions. The workflow does not approve or auto-merge PRs. Organization policy may need to permit this setting.
2. Merge the reviewed automation PR before relying on it. `.github/workflows/ci.yml` must exist on the default branch with `workflow_dispatch` support.
3. When ready for the first actual release, open npm's settings for `@simonteague6/skill-shelf` and add a **GitHub Actions** trusted publisher:
   - Organization/user: `simonteague6`
   - Repository: `skill-shelf`
   - Workflow filename: `release.yml` (not a path)
   - Environment: leave blank (the workflow does not use one)
   - Explicitly allow **npm publish**. New publishers default to stage-only; this workflow uses direct publication. Separate dist-tag management permission is not required.
4. Complete the first successful publication within **two days** of creating the trust, or delete the expired configuration and recreate it when ready. Do not create a release just to validate setup. No npm token, PAT, or repository secret is required.

Protect `main` with review and required CI checks as appropriate. Optional tag rules can restrict `v*` updates/deletion, but must allow GitHub Actions to create release tags. Optional environment approval requires changing the workflow and matching npm trust; it adds a per-release manual gate. After trusted publishing works, consider npm's **Require two-factor authentication and disallow tokens** setting. These settings require owner decisions; they are not changed by this PR.

See [npm trusted publisher setup, direct-publish permissions, and expiry](https://docs.npmjs.com/trusted-publishers/).

## Normal release

1. Review the generated release PR's version, changelog, package metadata, and license. Wait for CI on its current head before merging. Release Please uses `GITHUB_TOKEN`; a constrained dispatch job validates the same-repository bot PR, branch, base, pending label, and unchanged CI workflow, then dispatches CI **on trusted main** with the intended immutable PR SHA. Trusted preflight revalidates that head, rescheduling the current validated head if stale. Only the read-only test job checks out PR code; a separate trusted `checks: write` job attaches the result as `check` to the tested SHA. No recurring manual dispatch or PAT is needed. If branch protection requires a specific workflow/event rather than the `check` status, confirm compatibility on the first release PR.
2. Merge the release PR. The main-push workflow creates its tag and GitHub release, then passes `release_created`, tag, and SHA directly to its npm job. It does not rely on a tag/release event generated by `GITHUB_TOKEN` starting another workflow.
3. The npm job checks out the exact release commit, verifies stable version and lockfile agreement, tag identity, and main ancestry, and checks the public npm registry. An already-published version is skipped; only HTTP 404 permits publication. Registry/network errors fail the job.
4. For an unpublished version, the job runs `npm ci` and `npm run release:check`, including formatting, lint, type checks, tests, temporary packed CLI installation, and package-content inspection. Immediately before publishing, a guard from trusted main rejects versions older than registry `latest`; missing or invalid latest metadata and registry errors fail closed. The package's `files` allowlist excludes the guard checkout. Node 24 and npm >=11.5.1 support OIDC; release builds do not use dependency caches. npm publishes publicly to `latest`; trusted publishing automatically generates provenance for this public repository/package. Verify the npm package/version and workflow result.

Bookkeeping-only main pushes do not install dependencies or run release checks in the release workflow. Existing main CI still runs. An updated release PR adds one dispatched CI run: two short trusted API jobs surround one read-only test job. Full validation/publishing runs only for a newly created release or an explicit recovery. There are no schedules, matrices, polling loops, or new project dependencies. Hosted time varies; API-only bookkeeping is typically tens of seconds, not a free or zero-minute operation. Inspect Actions job timings for actual usage; standard Linux runners in public repositories are currently free under [GitHub's billing rules](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

## Recovery

A GitHub release can exist even if npm publication fails. Fix trust/registry problems first. In **Actions → Release → Run workflow**, select `main` and enter the existing stable tag, for example `v0.2.0`. This dispatch requires a published, non-prerelease GitHub release; it runs the same version/ancestry/package checks and skips versions already on npm without touching dist-tags. An unpublished historical version older than npm `latest` is rejected; prepare a new release instead of moving normal installs backwards. The latest check is not atomic with npm publication: external/manual publishers must not publish concurrently with this workflow. Do not rely on re-running the Release Please step to emit `release_created` again. Do not delete/recreate release tags or reuse npm versions. If faulty contents have already published, prepare a new version through the release PR process.

The initial hosted Release Please PR creation, automatic CI dispatch/check attachment, release creation, npm OIDC exchange, provenance, and recovery need verification after setup during an approved real release. Local checks cannot authenticate a trusted publisher; `npm whoami` is not an OIDC validation step.
